# AX investigations

The search application can delegate a bounded retrieval plan to AX. The serving API plans up to five searches, an AX task executes those searches with a short-lived capability, and the serving API generates a cited answer from the resulting authorized documents. This first implementation does not run arbitrary code generated by a model or author pull requests.

Every assistant question uses AX through the normal conversation composer. There is no backend selector or alternative assistant execution path. An unavailable AX installation returns an explicit error; it never silently substitutes a local task and claims that AX ran it.

## Permission boundary

The browser authenticates to the serving API with its existing identity. The serving pod retains that identity for the duration of the request. AX receives a random capability that authorizes only the indices of one fixed search plan, once each, for two minutes. The capability cannot change the query, choose a workspace, execute GraphQL, ingest records, or access model credentials.

Each retrieval calls the existing permissioned query API under the original identity. Source revisions and permissions are checked again before task completion and before each answer paragraph is released. The worker receives document identifiers, dates, and scores; source bodies remain in the serving API. Capabilities are revoked on completion, timeout, client disconnection, or serving-process restart. Task deletion is attempted even when execution fails.

AX and Substrate control APIs must remain private. A task capability is not permission to create or inspect other AX tasks. The AX CLI runs only in the trusted serving deployment and must not be exposed as a general user tool.

## Execution contract

- Task image: `services/investigator/Dockerfile`, using the pinned upstream AX runner.
- Coordinator: `services/search-api/investigation.py`.
- Worker: `services/investigator/investigator.py`.
- User endpoint: `POST /api/ask` (with `/api/investigate` retained as an alias), returning server-sent events using the existing answer protocol.
- Internal endpoints: `/internal/investigation/search` and `/internal/investigation/complete`. These require the run capability and must not be routed through the public proxy.
- Required deployment settings: `AX_SERVER`, `AX_INVESTIGATOR_IMAGE`, `POD_IP`, and optional `AX_ATESPACE` (default `context-search`).
- Same-cluster callbacks use the serving pod IP with TLS verification against `search-api`. A local cross-cluster trial may set the operator-controlled `AX_CALLBACK_HOST` and `AX_CALLBACK_PORT`; certificate verification remains enabled.

The SSE status messages describe actual stages. They are not model chain-of-thought. AX runner readiness is not evidence that the investigation completed: only the capability-protected completion callback permits answer synthesis.

## Building

Run `scripts/build-ax-tools.sh` to build the pinned AX CLI and runner. Set `AX_TARGET_ARCH` for the worker architecture. Generated binaries live in ignored `.build/`; upstream checkouts and the host CLI live in ignored `.runtime/`.

Build the investigator image from the repository root:

```sh
docker build -f services/investigator/Dockerfile -t YOUR_REGISTRY/context-investigator:ax-v1 .
```

The search API base image does not require AX. An AX-enabled serving image additionally needs the Linux `.build/ax` binary at `/usr/local/bin/ax`.

The pins are recorded in `services/harness/builder/upstream-lock.json`. Substrate is pinned to the revision consumed by AX's own Go module. The existing Docker Desktop Kubernetes 1.32 cluster lacks Substrate's required certificate APIs. The local AX trial therefore uses a separate Kind cluster with `ClusterTrustBundle`, `ClusterTrustBundleProjection`, and `PodCertificateRequest` enabled.

## Current limits

Runs belong to one live serving process and one HTTP stream. There is no durable background task inbox or reconnect/resume UI yet. A serving restart fails closed and requires retrying. Search capability lifetime is two minutes; the delegated user's token may expire earlier. The local pool has two workers. The coordinator admits at most two active investigations and emits a waiting status for queued requests, with a sixty-second queue limit. There are at most five searches and thirty source documents. The task cannot request arbitrary APIs or mutations.

The AX coordinator calls DeepSeek directly for planning and answer synthesis. No LiteLLM service or model gateway is required. Future AX agents can use separately delegated model and tool access, but this retrieval worker receives neither.

Automatic ingestion of investigation output is not enabled here: merging evidence from differently restricted entities requires preserving all source restrictions. The ordinary trajectory ingestion endpoint in the harness is available for explicitly scoped application events.

## Local trial deployment

The optional trial runs in a separate Kind cluster named `context-ax`, with its kubeconfig in ignored `.runtime/ax-kubeconfig`. The context graph remains on `docker-desktop`. Both clusters share Docker's memory allocation. The original 11.4 GiB allocation caused heavy swapping and restarts; the local trial was raised to 10 CPUs and about 14.4 GiB usable RAM. Keep additional application bundles stopped until the core workloads are healthy and memory headroom is confirmed. This is a development installation, not a highly available production deployment.

The deployment sources are under `deploy/ax/`: `workerpool.yaml` defines the Substrate gVisor workers, `render.py` renders the pinned upstream AX control plane with namespace-scoped secret access, and `investigation-local.yaml` installs a separate investigation coordinator alongside the existing search API. Build the coordinator with `services/search-api/Dockerfile.ax` and the AX control binaries with `scripts/build-ax-tools.sh`. Replace the local registry image references when using another registry.

`task-limits.patch` makes the pinned AX controller propagate CPU/memory limits to Substrate, use cold starts for credential-bearing investigation tasks, and fail if its task-specific template cannot be created. The investigator has a one-CPU, 256 MiB sandbox limit. AX's control API is private plaintext gRPC in this revision; do not publish it as a user-facing endpoint.

After the clusters and coordinator are running, keep the local bridges running in a terminal:

```sh
scripts/ax-local-bridges.sh
```

Restart the bridges after replacing the coordinator or AX server pod. Kubernetes port-forward binds to a particular pod. The search UI routes `/api/ask` and its `/api/investigate` alias to the coordinator; internal callback endpoints are not public UI routes. The trial requires one coordinator replica because capabilities live in that process. Restarts cancel active investigations; retries start a new task. This slice does not yet provide zero-downtime investigation handoff.

## Verified local behavior

The local trial completed through the search application's public proxy using an existing login: four searches ran in an actual AX/Substrate gVisor task, followed by eight streamed answer blocks with nine cited source documents. Each returned citation referenced a returned source. A second local identity without access to the knowledge workspace received HTTP 403 before an investigation started. The disposable network-policy test confirmed that deny rules actually block pod-to-pod traffic.

Search/coordinator tests cover unknown and expired capabilities, search-plan tampering, replay, completion prerequisites, permission revocation, disabled AX, and failed task status. The UI build, query tests, and patched AX controller tests passed. These checks establish this bounded retrieval path; they do not validate arbitrary agent-generated code, autonomous PR creation, or durable investigation recovery.

The default `/api/ask` route was verified after removing the mode selector: it started an AX task and streamed eight answer blocks with nineteen referenced sources. Three simultaneous requests then completed through the two-worker pool; the third emitted a capacity-wait status and completed after a slot was released. The non-AX assistant loop has been removed.
