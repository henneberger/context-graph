# Mandatory authorization architecture

Identity: verified RS256 OIDC JWTs (issuer, audience, signature/JWKS, exp, nbf, required subject). No caller-controlled user/group headers. Workspace selector X-Workspace-Id is untrusted input until SpiceDB verifies membership. A local development JWKS issuer and short-lived test credentials are provisioned separately; production supplies its OIDC issuer. HTTP development transport must be explicitly enabled. No auth-disabled runtime mode.

SpiceDB schema: user, workspace, entity. workspace relations administrator/member; permissions access=administrator+member, manage=administrator, view_schema=administrator+member. entity relations workspace:workspace (exactly one, provisioner enforced), restricted:user:*, reader:user, writer:user. view=((workspace->access - restricted)+reader+writer+workspace->manage)&workspace->access; ingest=(writer+workspace->manage)&workspace->access. Workspace members can view ordinary entities by default; a trusted operator adds entity:<resourceId>#restricted@user:* to require explicit reader/writer permission (administrators retain access). Removing this restriction restores workspace-wide visibility. Membership alone never grants write permission. An entity without its required workspace relation is denied, never auto-authorized. Resource ID is SHA256(workspaceId + NUL + entityId), lowercase hex. Workspace and entity grants are created only by trusted operator tooling, never auto-granted by ingestion. All checks fully consistent, no positive authorization cache; SpiceDB unavailable/conditional/unknown responses deny or return503, never allow.

Every ingestion envelope becomes schemaVersion2, includes required security:{workspaceId,resourceId,subjectId}. Server derives these from authenticated principal, requested workspace and entity ID after ingest permission check. Clients cannot supply trusted security values. New JSON bundle endpoints take X-Resource-Key separately from the document. Example endpoints can explicitly bind a JSON Pointer. Media X-Entity-Id currently supplies the same opaque permission resource key. Ingestion authenticates before reading upload, verifies resource before storing/publishing. Long uploads recheck before metadata publication and periodically during transfer. Unauthorized requests do not enter data/error topics with attacker-controlled metadata. Media has server-written sidecar JSON containing security provenance; media endpoints authenticate and check entity:view for every file/range/playlist request. No sidecar means deny. Nginx must proxy media to ingestion, never serve local alias. Responses private,no-store. Bearer HTTP and HttpOnly SameSite=Strict media-session cookie; POST session exchange requires Authorization and verifies JWT. Cookies cannot authorize ingestion writes. Token expiry closes sessions/subscriptions.

Shared Java module services/security, package io.contextgraph.security, artifact io.contextgraph:security:0.1.0. Public contract: SecurityContext record(subjectId,workspaceId,expiresAtEpochSecond); AccessControl.fromEnvironment(); authenticate(String authorization,String workspaceId); requireWorkspace(SecurityContext,String permission); allowed(SecurityContext,String resourceId,String permission); require(SecurityContext,String resourceId,String permission); static resourceId(workspaceId,entityId); exception AuthException.status() (401/403/503). authenticate verifies JWT and membership. require/allowed check expiry and require workspace membership (defense against mismatched entity relationship). String IDs validated (workspace [A-Za-z0-9_-]{1,64}, entity nonempty max256). KafkaSecurity.properties() loads required KAFKA_CLIENT_CONFIG secret file. HTTP SpiceDB client uses /v1/permissions/check and fully_consistent consistency. Query callers perform checks on bounded worker threads; no network calls on Vert.x event loop.

Flink trusts only authenticated ingestion Kafka principal, revalidates schema and canonical resourceId. Carry trusted workspace_id,resource_id,entity_id metadata alongside schema-defined columns. Carry scope through SQL results and use workspace+resource in every aggregation key and Kafka key. The schema-defined replacement starts with fresh tables, streams, and Flink state. Label removal/remapping is not a supported transform. Output schemas require labels. DLQ is operational/admin-only, never general query data.

Query HTTP authenticates Authorization and X-Workspace-Id, passes immutable SecurityContext through GraphQLContext. WS connection_init payload contains authorization and workspaceId; JWT expiry enforced for every operation/emission. Each stream event must match workspace and have required resource IDs, then fully consistent SpiceDB:view checks for all involved IDs immediately before delivery. No application field names implicitly create relationships or additional authorization rules. Failures terminate the operation; no silent fallback. Revoked users receive no further data after checks observe revocation. Checks do not retroactively retract bytes already delivered.

DuckDB source views are authorization-filtered BEFORE configurable SQL can aggregate/join/limit. Candidate resource IDs are discovered in the selected workspace, checked, then authorized-resource table joins constrain source rows; an explicitly registered multi-resource policy can require an additional resource. After query computation recheck authorized contributors before returning results (deny if revocation occurred). Never rely only on post-filtering result rows. SQL-derived API fields use the same path. Unlabeled/unregistered tables are denied, including schema discovery; schemas require view_schema and only registered secure tables. Physical metadata paths are not returned. Configured SQL must be single SELECT/CTE against source, no external functions/files/catalog access; stronger restrict DuckDB external access after constructing source view so SQL cannot bypass source. Trusted config is not end-user SQL. No result or authorization cache across principals.

Infrastructure: separate Kafka SASL_SSL credentials for ingestion (write endpoint/error topics), processor (read endpoints+group, write output/error+transaction IDs), query (read configured output/video+unique query groups), and admin provisioning. StandardAuthorizer deny by default, TLS verifies broker identity. Service credentials are Kubernetes Secrets, never ConfigMaps/images. SpiceDB/Postgres credentials likewise. Default-deny NetworkPolicies allow only explicit service paths and DNS/JWKS dependencies. Polaris vends warehouse credentials to separate processor writer and query reader identities. Ingestion holds only media-bucket credentials; Flink recovery uses a different bucket identity. Query and dashboard have no data volume; ingestion has bounded ephemeral staging. Users never receive catalog or S3 credentials. Configured multi-table queries authorize each source before the join, then recheck all contributors; see [lakehouse](lakehouse.md). Kubernetes node/cluster admins remain trusted operators; hostPath cannot protect against host root. Production needs TLS termination and restrictive RBAC/CNI enforcing policies.

Validation: two users in one workspace with disjoint entities plus another workspace; denied writes/queries/generated fields/schema/media; aggregates cannot incorporate forbidden rows; edge endpoint checks; forged/expired/wrong issuer/audience tokens; label forgery/missing labels; active WS/media revocation; SpiceDB outage fail closed; Kafka wrong-role produce/consume denied. Secure cluster smoke uses real SpiceDB and JWTs, not mocked permission checks alone.

## Connecting a production OIDC issuer

The APIs accept RS256 access tokens from a configured issuer. Set `OIDC_ISSUER` to the exact token issuer, `OIDC_AUDIENCE` to the API audience, and `OIDC_JWKS_URL` to that issuer's HTTPS JWKS endpoint on both ingestion and query. Provision SpiceDB user relationships using the issuer's stable `sub` values; no grants are inferred from JWT groups or an email address. Keep workspace selection explicit and authenticated as described above.

Replace the generated development truststore with one containing both the required internal service CAs and the issuer/JWKS certificate trust chain, and update the restricted egress policy for that JWKS endpoint. Public deployment needs HTTPS/WSS at the browser ingress. Do not turn on `SECURITY_ALLOW_HTTP` or disable hostname verification to connect an issuer.

The included password login form and `/auth/token` service are development fixtures, not a complete production OIDC authorization server or browser authorization-code flow. A production browser client must use its provider's authorization-code/PKCE integration, then send the resulting access token to the same GraphQL, subscription initialization and `/auth/session` contracts. Provider-specific client IDs, redirect URIs and user lifecycle management are deployment inputs.
