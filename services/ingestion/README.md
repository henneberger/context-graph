# Ingestion

Java 21 / Vert.x 5.2.0; `mvn -f services/ingestion/pom.xml package`, then from repository root `java -jar services/ingestion/target/ingestion-1.0.0.jar`.

Configuration: `CONFIG_PATH` (default `config/ingestion.json`), `PORT` (8080), `KAFKA_BOOTSTRAP_SERVERS`, `MEDIA_ROOT` (/data/media). Schema paths resolve relative to configuration. Each configured endpoint has a distinct topic. Every JSON input and every Kafka envelope/error is validated with JSON Schema draft 2020-12, including format assertions. Unknown JSON fields are preserved. Kafka publication uses idempotence and acks=all; JSON/image success is returned only after publication succeeds. Client retries can create new event IDs: transport retries are not deduplicated across requests.

Send raw JSON to `/ingest/events`, PNG/JPEG bytes to `/ingest/images`, or streaming MPEG-TS/other pipe-decodable video to `/ingest/video`. Set `X-Entity-Id` for media. Multipart uploads are not supported. Images are stored unchanged; metadata is read without decoding entire pixel buffers. Video passes through a bounded, backpressured pipe to FFmpeg; x264 output normalizes frame rate to 30fps, forces closed-GOP keyframes every 2 seconds and writes HLS independent MPEG-TS segments atomically. This intentionally transcodes source keyframes into a bounded interval to support the ten-second playback latency target. Actual latency depends on load, network and buffering and must be measured under deployment load.

Video responses stream NDJSON and immediately expose `X-Stream-Id` / `X-Playlist-Uri`. The first record has `status=streaming`; the final record has `status=complete` or `status=error`. Once streaming starts the HTTP status cannot change, so clients must inspect the final record. Chunk metadata goes to Kafka during the upload; media is served from `/media/`. An interrupted upload may leave valid earlier chunks and metadata. Files are retained: provision disk capacity and an external retention policy before long running loads. Failed Kafka publication leaves files available for inspection but is not silently retried as a successful ingestion.

`/health/live` and `/health/ready` support Kubernetes probes. Readiness checks Kafka topic metadata availability; it does not guarantee subsequent writes. SIGTERM refuses new ingestion, drains for 25 seconds and then closes. Active live uploads must reconnect during rolling deployments. Set pod terminationGracePeriodSeconds >= 45. Concurrent uploads and byte/duration limits bound process and buffering pressure; FFmpeg CPU limits should be set in Kubernetes.

`mvn test` verifies schemas and, when FFmpeg/ffprobe are available, transcodes a deliberately misaligned source GOP and verifies each resulting segment starts with a decodable keyframe. Kafka broker end-to-end verification requires the deployed stack.

The default JSON body limit is 900,000 bytes and entity identifiers are capped at 256 characters, leaving space for the envelope under Kafka’s default 1 MiB request limit. If you raise the body limit, raise producer/topic/broker message limits together. Image and segment files plus parent directory entries are forced to disk before publishing their metadata. Durability still depends on the mounted filesystem and device; local media is not replicated. Only playlist, segment, PNG and JPEG extensions are publicly served; FFmpeg logs stay private.

## Mandatory authorization

The service now requires the shared security module and schemaVersion 2 envelopes. Set `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`, `SPICEDB_ENDPOINT`, `SPICEDB_TOKEN`, and `KAFKA_CLIENT_CONFIG` (mounted SASL_SSL credential properties). Set `TLS_KEYSTORE_PATH` and `TLS_KEYSTORE_PASSWORD` for the HTTPS server. HTTP endpoints are allowed only with explicit `SECURITY_ALLOW_HTTP=true` for development; authentication remains mandatory. See `docs/security-architecture.md` and `services/security/README.md`.

Every write needs `Authorization: Bearer <JWT>` and `X-Workspace-Id`. JSON requires entityId; images/video require X-Entity-Id. Tokens are verified before upload handling, and SpiceDB checks workspace access plus entity ingest permission. Server-derived security labels are placed on every envelope. Incoming JSON `security` and `schemaVersion` fields are rejected. Endpoint topics are cg.secure.events, cg.secure.images and cg.secure.video, with operational errors in cg.secure.errors. Long transfers recheck permissions once per second and immediately before each metadata publication. Authorization failures never publish attacker-controlled error records.

Media requires verified identity plus entity view permission on every request, including playlists and byte ranges. Existing files without server sidecars are denied. Server-written sidecars carry entity and security provenance; file content is never an authorization source. All media responses use private,no-store. POST `/auth/session` with Bearer credentials and workspace exchanges a JWT for an HttpOnly SameSite=Strict cookie scoped to `/media/`; the cookie is Secure outside explicit HTTP development. The cookie embeds the signed short-lived token and is reverified against JWT expiry and SpiceDB on every request. Cookies never authorize writes. Dashboard nginx must proxy `/media/` and `/auth/session` to ingestion; it must not expose the media volume directly.

Decoder input is restricted to self-contained uploads. Images must have a PNG or JPEG signature before ImageIO examines metadata; image playlists, SVG, TIFF, GIF and WebP are not accepted by this profile. Video input uses FFmpeg's `pipe` protocol whitelist, preventing uploaded playlists or container references from opening local files or network URLs. FFmpeg still writes server-chosen HLS output paths normally. Metadata extraction does not invoke ffprobe on user input. Regression tests force HLS parsing to exercise the protocol boundary even on newer FFmpeg releases that already refuse playlist auto-detection through a pipe, and confirm no attempted network request reaches a local test server.
